== NAME

`hashsync` — run a command over SSH, deduplicating its output or input against indexed files

== SYNOPSIS

[verse]
--
`hashsync` ++[++`--profile` `name` ++|++ `--config` `path`++]++ ++[++`-q`++]++ ++[++`--no-human-readable`++]++ `subcommand` ++[++`argument ...`++]++
--

[verse]
--
`hashsync` `update` ++[++`--compact`++]++ ++[++`--rebuild`++]++ ++[++`--scan-immutable`++]++ ++[++`-j` `threads`++]++
`hashsync` `stats`
`hashsync` `prune` ++[++`--scan-immutable`++]++
`hashsync` `compact`
`hashsync` `ssh` ++[++`options`++]++ ++[++`-l` `user`++]++ ++[++`user`@++]++`host` ++[++`--`++]++ `command` ++[++`argument ...`++]++
`hashsync` `bench` ++[++`--block-size` `size`++]++ ++[++`--probe-threads` `threads`++]++
--

== DESCRIPTION

`hashsync` `ssh` runs a command on a remote host, much like [.Xr]#ssh(1)#, and deduplicates its standard output, its standard input, or both: data that the receiving host already has in its files is sent as a reference to a block of one of those files. By default, the command's standard output is deduplicated against files on the local host (a _pull_); with `--dedup-stdin`, standard input is deduplicated against files on the remote host instead (a _push_). Blocks are deduplicated at any offset, so this saves bandwidth whenever a stream repeats data that the receiving host already has, as with [.Xr]#tar(1)# archives, [.Xr]#rsync(1)# transfers, or package trees.

The local host is the _client_ and the remote host the _server_. The host that receives a deduplicated stream is its _receiver_, and the other host its _sender_. The receiver keeps an _index_ of the blocks in the regular files under the _roots_ listed in its configuration file (see [.Sx]#CONFIGURATION#). `hashsync` `update` creates the index or brings it up to date, and so does `hashsync` `ssh`, when it starts and again once the command has finished, unless `--no-update` is given. The receiver sends the sender its _hash list_, short hashes of all its blocks, which the sender looks for at every offset of the stream. Every match is verified against the receiver's files, so a file that changed since the last update only reduces deduplication; the output always matches the original stream exactly. Both hosts cache hash lists, so later transfers only send the changes.

The client starts `hashsync` on the server over two SSH sessions, which run the internal commands `hashsync` `serve` and `hashsync` `attach`. The server's shell looks `hashsync` up in its `PATH`, unless `--hashsync-path` gives its location.

The following options apply to all commands, and can be given before or after the command name:

`--config` `path`::
  Use the configuration file at `path` instead of a profile. Unless the file sets `index++_++path`, the index is named after the file, as for a profile, so files with the same name share an index.
`--no-human-readable`::
  Print byte counts in bytes instead of with units such as KiB, and the hash list sizes of `bench` as plain numbers.
`--profile` `name`::
  Use the profile `name`: the configuration file [.Pa]#~/.config/hashsync/#`name`[.Pa]#.toml#, with the index [.Pa]#~/.cache/hashsync/#`name`[.Pa]#.db# unless the file sets `index++_++path`. The name must not be empty or contain a slash. Without `--profile` or `--config`, the profile `default` is used. The two options cannot be combined, and `bench` accepts neither.
`-q`, `--quiet`::
  Print only warnings and errors.

`-h` or `--help` prints a short help text, for a specific command if given after its name, and `-V` or `--version` prints the version.

== COMMANDS

Files whose identity, size and change time are unchanged are not read again, and fully indexed immutable roots are not scanned at all. If `block++_++size` or `strong++_++hash` changed, the index is rebuilt. Files and directories that cannot be read are skipped with a warning.

`--compact`;;
    Compact the index at the end, like `compact`.

    Rebuild the index from scratch.
  `--scan-immutable`;;

  `-j` `threads`;;
    Number of threads that scan and hash, overriding the `threads` setting; 0 selects the default.

`prune` ++[++`--scan-immutable`++]++::
  Remove from the index the files and roots that no longer exist or cannot be reached, or that the configuration no longer includes, without hashing anything, then compact the index. `compact`::
  Compact the index by rewriting its database files without the data that updates and prunes have removed. The index must already exist and match the configuration.
`ssh` ++[++`options`++]++ ++[++`-l` `user`++]++ ++[++`user`@++]++`host` ++[++`--`++]++ `command` ++[++`argument ...`++]++::
  Run `command` on `host` over SSH, deduplicating its standard output, its standard input, or both. `hashsync` `ssh` passes its standard input to the command, copies the command's standard output and standard error back, and exits with the command's exit status. It accepts the arguments that [.Xr]#rsync(1)# passes to its remote shell, so `rsync -e 'hashsync ssh'` pulls with deduplication, and `rsync -e 'hashsync ssh --dedup-stdin'` pushes with it. As with [.Xr]#ssh(1)#, options may also follow `host`, and the command and its arguments are joined into a single line, which the server runs with the user's shell (`SHELL`, or [.Pa]#/bin/sh# if it is unset). A command that starts with `-` must follow `--`.
+
Both streams start immediately, while each receiver updates its index and sends its hash list, so deduplication improves as the list arrives. Each stream is buffered on both hosts in temporary files, so a slow reader does not hold up the command or the transfer until the buffers are full. Once `command` has finished, each receiver updates its index again, to add the files that the transfer has just written on that host while they are still cached in memory. `hashsync` `ssh` exits after this update. A failure of this update only prints a warning, and does not change the exit status.
+

  `--dedup-stdin`;;

  `--dedup-stdout`;;

  `--hashsync-path` `path`;;

  `--scan-immutable`;;

  `--ssh` `ssh-command`;;

== CONFIGURATION

All commands except `bench` read a configuration file in TOML format, by default [.Pa]#~/.config/hashsync/default.toml#, the file of the profile `default`. `--profile` and `--config` select another file; for `hashsync` `ssh`, they select the client's file, and `--server-profile` and `--server-config` select the server's. A configuration file only describes its own host. `hashsync` `ssh` needs one only on a host that receives a deduplicated stream, but a file named by an option must exist. Unknown keys are errors.

Each profile has its own index, and `hashsync` `ssh` deduplicates each stream against a single index. Data sets that share no content and are transferred separately, such as a Nix store and a photo collection, are best indexed in separate profiles. Updates are then faster, hash lists are smaller, and instances of `hashsync` `ssh` that deduplicate against different profiles do not wait for each other (see [.Sx]#CAVEATS#).

The following keys are recognized, all optional:

`block++_++size`::
  Size of the indexed blocks, at least 512 bytes; at least 4 KiB is recommended. Larger blocks make the index and the hash list smaller, but deduplicate less data. Changing it rebuilds the index. The default is `16KiB`.
`candidate++_++attempts`::
  How many indexed blocks with a matching hash the receiver tries before rejecting a match, at least 1. All copies of an immutable root count as one. The default is 128.
`hashlist++_++max++_++age`::
  How long this host keeps cached hash lists after the last transfer that used them, and the temporary files that `hashsync` leaves when it fails: a number of seconds, or a number followed by `s`, `m`, `h` or `d`, at least 1 second. A value below an hour gets a warning, since expiry could then remove the temporary files of a `hashsync` `ssh` that is still running. The default is `30d`.
`index++_++path`::
  Directory of the index, a RocksDB database. The default is [.Pa]#~/.cache/hashsync/#`name`[.Pa]#.db# for the file `name`[.Pa]#.toml#.
`roots`::
  The roots to index, as an array of tables written `++[[++roots++]]++`, with the keys described below.
`strong++_++hash`::
  Hash used to verify blocks: `blake3`, the default, or `sha256`. Changing it rebuilds the index.
`threads`::
  Number of threads that scan and hash files in an update, or look up paths in a prune. The default, 0, uses four per core, but at least 16 and at most 64.
`tmp++_++data++_++dir`::
  Directory for the temporary files of `hashsync` `ssh`, which disappear when it exits. Put it on a local disk; on tmpfs, the data would take up memory. The default is [.Pa]#~/.cache/hashsync/tmp-data#.

Each root accepts the following keys:

`path`::
  An absolute path, or a glob pattern of absolute paths; each match, a directory or a regular file, is a root. `++*++`, `?` and bracket expressions such as `++[++a-z++]++` match within a path component, and `++**++` across components. Matching compares bytes, is case-sensitive, and includes names that start with a dot. Symbolic links are not followed, and files and directories that cannot be reached do not match; they get a warning, like patterns without matches. Two roots with the same path, or one inside the other, are an error. An update also fails if a mount makes it reach the same directory twice, as with a bind mount of a directory that a root contains, or of a parent directory; exclude the mount point, or set `one++_++filesystem` for a mount below a root. This key is required.
`exclude`::
  Patterns of files and directories to leave out, together with everything below them. A pattern that starts with `/` matches absolute paths; any other pattern matches names, and cannot contain a slash.
`identifier`::
  How an immutable root names its _group_: matches with the same identifier are _copies_ of the same content, which the index stores once. `"path"`, the default, uses the absolute path of the match; `"name"` its last component; `++{++ strip++_++prefix = "/mnt/disk" }` the path without that prefix; and `++{++ literal = "photos-2019" }` that fixed name.
`immutable`::
  If true, `hashsync` assumes that the contents of the root never change. An update indexes a group once, from its first copy that exists, and then reuses it without reading it, until `--scan-immutable` or `--rebuild`, or until an update finds none of its copies, which removes the group. If the contents change anyway, transfers are still correct, but deduplicate less until the group is indexed again. The receiver reads blocks from any copy. All copies of a group must have the same `exclude` patterns and `one++_++filesystem` setting. The default is false.
`may++_++vanish`::
  If true, the root need not exist: it gets no warning when it does not, and if a copy of a group disappears before the update scans it, the next copy is scanned instead. A group whose copies are all on an unmounted disk is still removed, and indexed again when the disk is back. The default is false.
`one++_++filesystem`::
  If true, leave out files and directories on a different mount than their parent directory. Unlike `rsync -x`, this compares mounts rather than devices. The default is false.

Sizes, in the configuration file and in options, are a number of bytes, or a number followed by `KiB`, `MiB`, `GiB` or `TiB`, or by `KB`, `MB`, `GB` or `TB` for powers of 1000, in any case. In the configuration file, sizes and durations can also be integers.

Paths, patterns and identifiers are byte strings: after TOML parsing, `++\++xHH` stands for a byte and `++\\++` for a backslash, and any other backslash is an error, except in patterns, where `++\*++`, `++\++?`, `++\[++`, `++\]++`, `++\++-`, `++\++!` and `++\++^` match those characters literally, as does a byte given as `++\++xHH`. Single-quoted TOML strings avoid doubling the backslashes. In `index++_++path` and `tmp++_++data++_++dir`, `~` and a leading `~/` stand for the home directory, and other relative paths are relative to the working directory, which on the server is the home directory.

If `hashsync` fails, it can leave temporary files whose names start with `.hashsync-` in the caches and in `tmp++_++data++_++dir`; `hashsync` `ssh` removes them once they are older than `hashlist++_++max++_++age`.

== EXIT STATUS

`hashsync` `ssh` exits with the exit status of `command`, 128 plus the number of the signal that terminated it, or 127 if it could not be started, even if the program reading its output exited early. If `hashsync` `ssh` itself fails, for example because SSH cannot reach the host, it exits with 1, or with 128 plus the signal number after SIGINT or SIGTERM.

The other commands exit with 0 on success, even if they skipped files or directories that cannot be read, and 1 on failure. Usage errors exit with 2. A bug, or an error in the index database such as corruption, aborts `hashsync` with SIGABRT, which shells report as status 134.

== EXAMPLES

Copy a directory from the host `nas` over an older local copy of it, which the local index covers:

....
hashsync ssh -n backup@nas tar -C /srv/data -cf - . |
    tar -C /srv/data -xf -
....

The same in the other direction, deduplicated against the index on `nas`:

....
tar -C /srv/data -cf - . |
    hashsync ssh --dedup-stdin backup@nas tar -C /srv/data -xf -
....

Use `hashsync` as the remote shell of [.Xr]#rsync(1)#, to pull and to push. Deduplication is much more effective with a patched rsync (see [.Sx]#CAVEATS#). With `--delete-delay`, rsync deletes files only after the transfer, so files that are about to be deleted, such as the old names of renamed files, can still be used for deduplication:

....
rsync -a --delete-delay -e 'hashsync ssh' nas:/srv/data/ /srv/data/
rsync -a --delete-delay -e 'hashsync ssh --dedup-stdin' \
    /srv/data/ nas:/srv/data/
....

Run the server from a statically linked binary in the remote home directory:

....
hashsync ssh -n --hashsync-path bin/hashsync nas cat big.iso > big.iso
....

The default profile, in [.Pa]#~/.config/hashsync/default.toml#, for the data directory of the examples above:

....
block_size = "16KiB"

[[roots]]
path = "/srv/data"
exclude = ["*.tmp", ".cache"]
one_filesystem = true
....

A profile for two Nix stores at separate locations, in [.Pa]#~/.config/hashsync/nix.toml#, which `--profile nix` selects:

....
[[roots]]
path = "/nix/store/*"
immutable = true
identifier = "name"
exclude = [".links"]
may_vanish = true

[[roots]]
path = "/mnt/disk/nix/store/*"
immutable = true
identifier = "name"
exclude = [".links"]
....

A root whose name contains the byte FF, which is not valid UTF-8, and exclusions of the literal names `literal++*++name` and `back++\++slash`:

....
[[roots]]
path = '/srv/archive-\xFF'
immutable = true
identifier = { literal = 'archive-\xFF' }
exclude = ['*.tmp', 'literal\x2Aname', 'back\\slash']
....

== DIAGNOSTICS

Messages go to standard error. Notes report progress and summaries, and `-q` suppresses them; messages from the server are marked as such. Paths and other values from outside the program are shown in the byte-string syntax of the configuration file.

== CAVEATS

Each index has a lock, and commands that modify the index, such as `hashsync` `update`, wait until they can hold it exclusively. `hashsync` `ssh` holds the lock exclusively for its updates at the start and after the command, and shares it with other readers in between, until the stream has ended. While its update at the start waits for the lock, the stream is sent without deduplication (unless `--wait` is given, in which case the stream is not sent until the update has finished). With `--no-update`, `hashsync` `ssh` skips both updates and so only needs a read-only lock, which several instances can hold at the same time.

The lock can cause a deadlock if the `command` that `hashsync` `ssh` runs on the server itself runs a `hashsync` command that needs exclusive access to an index, such as `hashsync` `update`. For example, `hashsync ssh --dedup-stdin nas 'hashsync update; tar -xf -'` never finishes: the update waits for the lock, which is only released once [.Xr]#tar(1)# has read all of its standard input. Two `hashsync` `ssh` commands in opposite directions between the same two hosts can also deadlock if each one's `command` runs `hashsync` `update` on its server, since each update then waits for the other `hashsync` `ssh`.

[.Xr]#rsync(1)# sends file data in pieces of at most 32 KiB, which makes deduplication ineffective. To deduplicate rsync transfers effectively, the rsync that sends the files needs a patch that raises this limit to 8 MiB; the patch is backwards compatible, so the other rsync can be unpatched.

If SSH multiplexes sessions over one connection, for example with `ControlMaster`, `hashsync` `ssh` still works, but the sender's questions about matching blocks wait behind the data of the streams.

== SECURITY CONSIDERATIONS

The sender of a deduplicated stream learns a hash of every block in the receiver's index, and can test whether the receiver has a block with given contents. In a push, the client could read the indexed files through its SSH login anyway, but in a pull, the server learns about the client's files, so only pull from servers that you trust. Even a trusted server keeps the client's hash lists in its cache after a pull, where anyone who later gains access to the server can read them. `--no-sender-cache` asks the server not to keep them. It does not protect against an untrusted server, which still receives the hashes and can ignore the request.
